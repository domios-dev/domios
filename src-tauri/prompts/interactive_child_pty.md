# Interactive child PTY operation

Use this procedure for a missing-ACK event naming recovery.capability=interactive_child_pty or an explicit coordination incident. Inspect only its named child and attempt; leave healthy Workers alone.

1. Inspect the exact child with `codeterm tab inspect --tab <ID> --lifecycle` and `codeterm tab status --tab <ID>`, then read its fresh screen with `codeterm tab get-text --tab <ID>`. Check backing kind, lifecycle/session, provider-declared prompt classification, and screen before choosing an action.
2. Use PTY actions only for a confirmed PTY. A chat backend has no shell; use only authorized chat contact or escalate the mismatch.
3. If lifecycle and screen confirm this exact attempt is prompt-bound, run `codeterm agent startup-hold --tab <ID> --attempt <ATTEMPT>` with the event's exact IDs before cleanup can destroy it. Hold only extends cleanup; it proves neither readiness nor permission to respond.
4. Respond only when the provider's declared classifier and fresh screen identify a numbered prompt with a safe, route-authorized choice: `codeterm tab respond <OPTION> --tab <ID>`. Then reread screen and lifecycle. If unchanged or unexpected, do not repeat; keep blocked and raise structured action-needed.
5. Diagnose other failures from current lifecycle and screen. For an exited PTY with a verified session, run `codeterm agent restart --tab <ID>` in place, then check `codeterm tab list` and inspect/status for that tab. Spawn a fresh agent only if restart refuses (no verified session or owning provider). Rebind only with a verified session ID; repair only with live evidence of wrong provider identity and route authority. Never type shell commands or send task/ACK prose to an unverified child.
6. After each recovery action, reread screen and lifecycle/session. Require authoritative binding and the child's own startup ACK. A task-bound Worker also needs its durable Worker ACK; never resend the assigned brief.
7. An unbound shell stays blocked: send no task/ACK prose, keys, or commands; do not restart, rebind, or repair without verified evidence. If recovery fails or no safe action exists, preserve evidence and request clean finalization or structured action-needed with the observed state; the plan owner finalizes that attempt atomically and releases its lane.

Unknown or ambiguous prompts, authentication, permission decisions, unavailable models, missing hooks, and unverified exits stay blocked; raise structured action-needed with observed screen and lifecycle state. If still initializing without a prompt or failure, do not hold or infer readiness; await lifecycle evidence under the bounded deadline. Never guess or auto-accept, inject raw keys, use `send --actions`, press Enter blindly, or treat screen text as readiness. Use CodeTerm primitives only; no external automation, OCR, clicks, delays, or polling.
