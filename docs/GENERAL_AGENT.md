# General Agent — Current Behavior

The General Agent (GA) is the protected, always-on agent for one CodeTerm installation. It lives in the General workspace, represents this machine in the mesh, can coordinate project agents, and receives bridge traffic such as Telegram or mesh messages.

This document describes the shipped implementation. It is not the old phase roadmap.

## Files

Root: `~/.codeterm/` on macOS/Linux or `%USERPROFILE%\.codeterm\` on Windows.

```text
~/.codeterm/
├── general/
│   ├── AGENT.md      # generated from src-tauri/prompts/general_agent.md
│   ├── CLAUDE.md     # generated wrapper: @./AGENT.md
│   ├── AGENTS.md     # generated Codex bundle: AGENT.md + provider rules
│   ├── bootstrap.md  # created once on first boot, then removed by the GA
│   ├── identity.md   # user/installation identity, read into AGENT.md
│   └── soul.md       # GA tone/personality, read into AGENT.md
├── mem/
│   └── knowledge.db  # persistent memory store
├── secrets/          # daemon token files such as telegram.token
├── logs/
└── config.toml
```

There are no generated marker blocks. `AGENT.md`, `CLAUDE.md`, and `AGENTS.md` are regenerated by CodeTerm and should not be user-edited. Persist user identity in `identity.md`, agent personality in `soul.md`, and durable operational facts in `codeterm mem`.

Secrets are not human-readable markdown files. User credentials live in `codeterm mem secret`, backed by the local OS keychain by default or Bitwarden/Vaultwarden when configured. Daemon-internal bridge tokens are file-based under the configured secrets directory; see `codeterm docs SECRETS`.

## Prompt Generation

Implementation: `src-tauri/src/service/general_agent/instructions.rs`.

`generate_instructions()` writes:

- `AGENT.md` from `GENERAL_AGENT_TEMPLATE`
- `CLAUDE.md` as a minimal `@./AGENT.md` wrapper
- `AGENTS.md` as the rendered GA prompt plus `CODETERM_RULE` and `BRIDGE_MEM`
- `bootstrap.md` only when it does not already exist

`render_agent_md()` substitutes:

- `{version}`
- `{platform}`
- `{hostname}`
- `{provider_name}`
- `{general_dir}`
- `{secrets_dir}`
- `{skills_dir}`
- `{identity}`
- `{soul}`
- `{wake_up}`
- `{codeterm_cli}`

The live memory snapshot comes from `mem wake-up` when available. If mem is unavailable, prompt generation logs the failure and injects an empty wake-up section so GA startup does not fail because memory is temporarily locked.

## Bootstrap

On first boot, CodeTerm writes `bootstrap.md` into the General workspace. The fresh-session init message tells the GA to check that file for `<!-- bootstrap: true -->` and follow it.

The bootstrap flow is intentionally conversational:

1. Detect OS locale.
2. Ask what to call the user.
3. Demonstrate two or three CodeTerm capabilities.
4. Capture the minimum identity.
5. Write `identity.md` and `soul.md`.
6. Save the canonical identity preference to mem.
7. Delete `{general_dir}/bootstrap.md`.

## Lifecycle

Startup:

1. Ensure the General directory exists.
2. Regenerate prompt files.
3. Ensure the protected General workspace and pane exist.
4. Resume the existing provider session when possible; otherwise launch a fresh agent.
5. For fresh launches, send a one-time init message that tells the GA to read the live mem snapshot, run `codeterm mesh peers`, and acknowledge readiness.

Resume sessions deliberately do not receive the init message because the provider replays previous context.

Shutdown and app restart rely on normal session persistence. If the GA needs to restart itself, it should use `/exit`; CodeTerm resumes it.

## Protected Workspace And Pane

| Property | Current behavior |
|---|---|
| Workspace | General workspace, protected from close |
| Pane alias | `general` |
| CWD | `{general_dir}` |
| Provider | Configured agent provider |
| Permissions | Skip-permissions launch where the provider supports it |
| Role | Orchestrator |

`codeterm send-text "..." --pane general` resolves the alias to the protected pane.

## Bridge And Mesh Routing

The GA prompt has a prefix table for inbound channels. The prefix is the return address:

- `[Telegram: USER_ID ...]` replies via `codeterm bridge send --to USER_ID --service telegram`.
- `[Mesh: PEER pane=ID ...]` replies via `codeterm send-text --pane ID --mesh PEER`.
- `[Report from PANE_ID]` is a child report; act on it or forward the summary to the original user channel.

Telegram and other bridge details live in the operational playbooks:

- `codeterm docs TELEGRAM-SETUP`
- `codeterm docs TEXT-HOOKS`
- `codeterm docs CONFIG`

## Memory And Skills

`codeterm mem` is the persistent source of truth. The GA prompt receives the mem protocol through provider rules and the CLI reference; the generated prompt also contains the live wake-up section when available.

Skills are file-backed under the configured CodeTerm skills directory and synced by the watcher to provider-specific skill directories. Do not write directly into `~/.claude/skills/` or `~/.agents/skills/`.
