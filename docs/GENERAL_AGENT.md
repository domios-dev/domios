# General Agent — Current Behavior

The General Agent (GA) is the protected, always-on agent for one CodeTerm installation. It lives in the General workspace, represents this machine in the mesh, can coordinate project agents, and receives bridge traffic such as Telegram or mesh messages.

This document describes the shipped implementation. It is not the old phase roadmap.

## Files

Root: `~/.codeterm/` on macOS/Linux or `%USERPROFILE%\.codeterm\` on Windows.

```text
~/.codeterm/
├── general/
│   ├── AGENT.md      # generated from src-tauri/prompts/general_agent.md
│   ├── CLAUDE.md     # generated wrapper: @./AGENT.md
│   ├── AGENTS.md     # generated Codex bundle: AGENT.md + provider rules
│   ├── bootstrap.md  # created once on first boot, then removed by the GA
│   ├── identity.md   # user/installation identity, read into AGENT.md
│   └── soul.md       # GA tone/personality, read into AGENT.md
├── mem/
│   └── knowledge.db  # persistent memory store
├── secrets/          # daemon token files such as telegram.token
├── logs/
└── config.toml
```

There are no generated marker blocks. The `AGENT.md`, `CLAUDE.md`, and `AGENTS.md` files inside the General directory are regenerated by CodeTerm and should not be user-edited. Persist user identity in `identity.md`, agent personality in `soul.md`, and durable operational facts in `codeterm mem`.

Secrets are not human-readable markdown files. User credentials live in `codeterm mem secret`, backed by the local OS keychain by default or Bitwarden/Vaultwarden when configured. Daemon-internal bridge tokens are file-based under the configured secrets directory; see `codeterm docs SECRETS`.

## Prompt Generation

Implementation: `src-tauri/src/service/general_agent/instructions.rs`.

`generate_instructions()` writes:

- `AGENT.md` from `GENERAL_AGENT_TEMPLATE`
- `CLAUDE.md` as a minimal `@./AGENT.md` wrapper
- `AGENTS.md` as the rendered GA prompt plus `CODETERM_RULE` and `BRIDGE_MEM`

The first-run completion path creates `bootstrap.md` once. Routine prompt
regeneration never recreates it after the GA removes it.

`render_agent_md()` substitutes:

- `{version}`
- `{platform}`
- `{hostname}`
- `{provider_name}`
- `{general_dir}`
- `{secrets_dir}`
- `{skills_dir}`
- `{identity}`
- `{soul}`
- `{wake_up}`
- `{codeterm_cli}`

The live memory snapshot comes from `mem wake-up` when available. If mem is unavailable, prompt generation logs the failure and injects an empty wake-up section so GA startup does not fail because memory is temporarily locked.

## Bootstrap

On first boot, CodeTerm writes `bootstrap.md` into the General workspace and
delivers its contents as a separate confirmed message after the permanent
system prompt. Bootstrap is not part of the system prompt and is not sent on
resume.

The bootstrap flow is intentionally conversational:

1. Detect OS locale.
2. Ask what to call the user.
3. Demonstrate two or three CodeTerm capabilities.
4. Capture the minimum identity.
5. Write `identity.md` and `soul.md`.
6. Save the canonical identity preference to mem.
7. Delete `{general_dir}/bootstrap.md`.

## Lifecycle

Startup:

1. Ensure the General directory exists.
2. Regenerate prompt files.
3. Ensure the protected General workspace and tab exist.
4. On picker completion, consume a durable fresh-session intent and never scan
   global provider sessions by CWD.
5. Otherwise resume the explicitly owned provider session when possible.
6. Deliver the permanent General prompt once through the provider's generated
   native startup instructions or durable confirmed fallback.
7. On the first fresh launch only, deliver `bootstrap.md` as a separate message.

Resume sessions deliberately do not receive bootstrap because the provider
replays previous context.

Shutdown and app restart rely on normal session persistence. Manual GA restart uses the General Agent restart control; do not assume a manual `/exit` preserves context.

## Protected Workspace And Tab

| Property | Current behavior |
|---|---|
| Workspace | General workspace, protected from close |
| Tab aliases | `general`, `main` |
| CWD | `{general_dir}` |
| Provider | Configured agent provider |
| Permissions | Skip-permissions launch where the provider supports it |
| Role | Orchestrator |

`codeterm send "..." --tab general` and `codeterm send "..." --tab main` resolve to the protected tab.

## Bridge And Mesh Routing

The GA prompt keeps only a short routing reminder. The authoritative command table lives in the injected CLI reference. Routed prefixes name return addresses; `codeterm:system` is a host event with no source Tab and is never replied to:

- `-=-codeterm:telegram user=USER_ID ...-=-text` replies via `codeterm bridge send --to USER_ID --service telegram`.
- `-=-codeterm:tab label=NAME tab=ID ...-=-text` replies via `codeterm send --tab ID`.
- `-=-codeterm:mesh peer=PEER tab=ID-=-text` replies via `codeterm send --tab ID --mesh PEER`.
- `-=-codeterm:report from=NAME tab=ID ...-=-text` is a child report; act on it or forward the summary to the original user channel.
- `-=-codeterm:system context=KIND-=-text` is host input; act on it or ignore it, never send a reply.
- `-=-codeterm:hook ...-=-metadata` is already routed by a text hook; trust the metadata and follow the inbound language.

Telegram and other bridge details live in the operational playbooks:

- `codeterm docs TELEGRAM-SETUP`
- `codeterm docs TEXT-HOOKS`
- `codeterm docs CONFIG`

## Memory And Skills

`codeterm mem` is the persistent source of truth. The GA prompt receives the mem protocol through provider rules and the CLI reference; the generated prompt also contains the live wake-up section when available.

Skills are documented in the injected CLI reference. The GA prompt does not duplicate the skill authoring rules.
