## Why we're doing this (context)

During the v1.1.22 release session we hit three classes of mem-graph problems that were not covered by the v1.1.21 normalize-phase fix:

1. **Graph reads leak invalidated edges everywhere** — three separate SQL bugs (one in `graph_full`, two in `graph related`/`traverse`) that all return `valid_to NOT NULL` rows as if they were active. The visualization, CLI graph queries, and the dreaming pipeline all see invalidated edges as live.
2. **The Dreamer/normalize/repair flows touch the database directly via raw SQL** — every fix (broken-rel invalidation, alias merge, orphan cleanup, my recent revive script) reaches into `mem_items`/`relations`/`entities` tables with hand-written UPDATE/DELETE. There is no canonical route layer that enforces invariants (e.g. "endpoint must exist in entities OR mem_items"). The result: each new bit of cleanup is its own bug surface, and the Dreamer cannot safely do the kind of re-clustering I did manually today (introduce intermediate `topic_*` / `role_*` nodes, re-route content edges, hard-delete duplicates).
3. **Visualization shows model identifiers that are version-pinned and confusing** — `claude-sonnet-4-6`, `claude-opus-4-7`, `claude-haiku-4-5-20251001` appear in the picker UI and various places. Andrey wants these collapsed to canonical short labels (`sonnet`, `opus`, `haiku`) at the user-facing layer, while the actual API call still resolves to the current concrete model id at runtime.

This plan also bundles a Dreamer evolution: teach it to do graph hygiene tasks the way a human (me, today) would do them — but always through routed APIs, never raw SQL.

## Hard rules

- **No raw SQL outside the `mem::store::*` write layer.** Dreamer, repair commands, normalize phase, and any future graph maintenance task must call typed Rust functions (`graph_relate`, `graph_invalidate`, `graph_alias`, `graph_purge`, `graph_route_through`, etc) that go through the central manager. The store layer is the only place that talks to SQLite.
- **Graph reads default to active-only.** `valid_to IS NULL` is the default filter for every query (`graph_full`, `graph related`, `graph traverse`, `graph path`, `graph tunnels`). Historical / invalidated edges are opt-in via an explicit `--as-of <date>` or `--include-invalidated` flag.
- **No string-based timestamp comparisons.** Whenever the SQL has `valid_to > X`, both sides must go through `datetime(...)`. Add a unit test with a deliberately ISO-formatted `valid_to` and a SQLite `datetime('now')` to pin the regression.
- **No new top-level CLI subcommands without a brainstorming pass.** All v1.1.23 names locked in §Decisions D4 below. Don't relitigate.
- **Dreamer LLM phase is opt-in.** Any LLM-driven re-clustering must be triggered explicitly, never on a cron by default. The user pays the tokens and accepts the risk; the system does not silently spend on graph rewrites.

### D1 — Model picker labels (Track 5)

**Fully unpinned short labels: `sonnet` / `opus` / `haiku`.**

- One source of truth (`src-tauri/src/agent/models.rs`) maps each short label to the current concrete model id. When Anthropic rolls a new version, exactly one constant changes.

### D2 — Re-cluster review UX (Track 4)

**Markdown plan file with YAML-fenced action blocks, edit-then-apply.**

- Dreamer (heuristic or LLM) writes the plan to `~/.codeterm/mem/dream-plans/<utc-ts>.md`.
- Human-readable narrative (one section per proposed cluster: name, motivation, member list).
- Each actionable mutation lives inside a ` ```yaml ` fence so `mem dream apply <file>` can re-parse it. User edits inside the fences; deleting a section deletes the action.
- Malformed or missing fence → that single action is skipped with a `WARN` to stderr, not a hard abort. Whole-file errors do abort.
- After apply, the file is renamed `<utc-ts>-applied.md` (with an inline summary of which actions ran, which were skipped, and any errors). Rejected sections are preserved in the file as the audit trail.

### D3 — Dreamer SQL refactor dependency model (Track 3)

**Extract a new workspace crate: `codeterm-mem-store`.**

- New crate at `crates/mem-store/` (or `cli/mem-store/` — nail down during writing-plans).
- Dependencies: `rusqlite + chrono + serde + thiserror` only. No tokio, no Tauri, no reqwest.
- Houses the typed graph mutation API: `graph_relate`, `graph_invalidate`, `graph_alias`, `graph_route`, `graph_purge_invalidated`, `graph_revive_broken`, `graph_introduce_topic`, plus the read helpers used by both worker and daemon.

### D4 — CLI naming (Track 2)

Locked subcommand and flag names. Style follows existing `mem graph` verbs (`relate`, `related`, `invalidate`, `alias`, `traverse`).

```

mem graph route                --from <id> --to <id> --via <id>
                               [--rel-in <type>] [--rel-out <type>]

                               [--dry-run]

mem graph related     ... [--include-invalidated]
mem graph traverse    ... [--include-invalidated]
mem graph full        ... [--include-invalidated]
mem graph path        ... [--include-invalidated]
mem graph timeline    ... [--include-invalidated]

# Dreamer review/apply (Track 4)
mem dream suggest-clusters     [--threshold 25] [--out <path>]
mem dream llm-recluster        [--threshold 25] [--out <path>]
mem dream apply                <plan-file>
```

Naming rationale (don't relitigate later):

- `route` (one word) over `route-through` / `reroute` — matches existing single-verb style.
- `purge-invalidated` (explicit) over `purge` — the latter reads dangerously; we want the verb to telegraph "only invalidated rows".
- `revive-broken` lives under `graph`, not `repair`. The v1.1.22 `mem repair revive-broken-relations` command stays as a back-compat alias — both call into the same `codeterm-mem-store::graph_revive_broken` function.
- `introduce-topic` over `cluster` — the latter collides with Track 4's re-clustering concept.
- `--from --to --via` mirrors existing `--from --to --rel` flag set.
- `--include-invalidated` (default off) is the only opt-in escape hatch for historical reads, alongside `--as-of <date>` (already shipped).
- `mem dream apply <file>` takes a positional path, not `--plan` — matches `mem repair revive-broken-relations` and other "act on a thing" commands.

## Tracks

Five independent tracks. Land in this order or in parallel — they don't conflict.

### Track 1 — Graph read filtering (the three bugs)

**Files:**
- `src-tauri/src/mem/store/query.rs::graph_full` — currently `WHERE valid_to IS NULL OR valid_to > datetime('now')`. The string compare is broken because stored `valid_to` is ISO `2026-05-08T06:43:16.795764+00:00` and `datetime('now')` returns `2026-05-08 06:43:16` — `T` (0x54) > space (0x20) so the second clause is always true.
- `src-tauri/src/mem/graph.rs::related` — no `valid_to` filter at all when `as_of` is `None`. Returns every row, including invalidated.
- `src-tauri/src/mem/graph.rs::traverse` — same pattern as `related`.
- (also check `graph_path`, `graph_tunnels`, `graph_timeline` for the same bug class.)

**Fix:**
- Replace `valid_to > X` with `datetime(valid_to) > datetime(X)` everywhere both sides aren't already canonicalized.
- When `as_of` is `None`, default to `valid_to IS NULL` (active-only).
- When `--as-of <date>` is provided, the query becomes `valid_from <= ?date AND (valid_to IS NULL OR datetime(valid_to) > datetime(?date))`.
- Add `--include-invalidated` flag at the CLI / API surface for the rare audit-trail / debug case. Default off.

**Tests:**
- Insert a relation with `valid_to = '2026-01-01T00:00:00.000000+00:00'` (clearly past). Run `graph_full` — relation must NOT appear in the output.
- Insert a relation with `valid_to = NULL`. Run `graph related --id X`. Must appear.
- Run `graph related --id X --as-of '2025-12-01'` against the historical row above. Must appear (it was active on that date).
- Run `graph related --id X --include-invalidated`. Must include the invalidated row regardless of date.

### Track 2 — Route layer for graph mutation

Currently the only graph-write APIs are `graph relate`, `graph invalidate`, `graph alias`. Manual cleanup needs more.

Add to `src-tauri/src/mem/graph.rs` (and matching CLI subcommands under `mem graph`):

- `graph_purge_invalidated(scope: PurgeScope, before: Option<date>)` — hard-delete relations whose `valid_to` is set and (older than the cutoff OR matches the scope filter, e.g. only relations invalidated by a specific reason such as "broken-rel-cleanup"). Always logs how many were deleted. Audit row written to `graph_purge_log` table (new) so we can answer "what got hard-deleted on date X" later.
- `graph_route_through(from: id, to: id, via: id, rel_type_in: str, rel_type_out: str)` — invalidate the direct (from → to) edge and create (from → via → to). Used to introduce a topic intermediate. Atomic.
- `graph_revive_broken_relations(since: Option<date>)` — un-invalidate relations whose endpoints exist in entities OR mem_items. Idempotent. The recovery flow I ran manually as Python today.
- `graph_introduce_topic(topic_id, entity_type, sources: Vec<id>, anchor: id)` — atomically creates a topic intermediate, links sources → topic, topic → anchor, invalidates old direct sources → anchor edges. Used when re-clustering a hub.

CLI surface and flag names are locked — see §Decisions D4. Track 2 implements the typed Rust functions in the new `codeterm-mem-store` crate (D3) and wires the CLI subcommands through them.

The repair CLI track from v1.1.22 (`mem repair revive-broken-relations`) ALREADY shipped a basic version of `graph_revive_broken_relations`. Track 2 promotes it into the canonical graph mutation layer next to the other route-through helpers — both `mem repair revive-broken-relations` (back-compat alias) and the new `mem graph revive-broken` call into the same function.

A new `relations.reason` column is required for the `--reason <substr>` filter on `purge-invalidated`. If it doesn't already exist on the table, Track 2 adds it via migration along with the new `graph_purge_log` audit table. Existing rows get `NULL` reason; new mutations populate it where meaningful (e.g. `'broken-rel-cleanup'`, `'route-through-introduce-topic-<topic-id>'`).

### Track 4 — Dreamer learns to re-cluster (LLM-driven, opt-in)

The manual re-clustering I did today (machine_blackstar → role_release_host_windows / role_main_dev_workstation / topic_codeterm_mesh_topology, project_codeterm → 5 topic intermediates, etc.) is a repeatable pattern. Teach the Dreamer to do it.

Two phases:

Review UX locked — see §Decisions D2 (markdown plan with YAML-fenced action blocks, edit-then-apply). Both phases below produce the same plan format.

**4a. Heuristic re-cluster** (no LLM, deterministic):
- Find hubs with degree > N (configurable, default 25).
- Group incident edges by `relation_type`. If a single relation_type accounts for ≥40% of edges, that's a candidate for an intermediate.
- Suggest a topic name from existing entity prefixes (`tech_*` → `topic_<area>_tech`, `learning_v1_1_*` → `topic_codeterm_release_history` if not already there).

- CLI: `mem dream suggest-clusters [--threshold 25] [--out <path>]`.

**4b. LLM-driven re-cluster** (opt-in, costly):
- Same input (hubs + edges + node titles/summaries).
- Prompt a Claude Sonnet/Opus call to propose topic groupings with names that semantically reflect the content. Default model = `sonnet` (per D1 short-label scheme).
- Output the same markdown plan format as 4a; the LLM only drafts the action blocks, the apply step is identical.
- Apply via the typed mutation helpers from `codeterm-mem-store` — never direct SQL.
- CLI: `mem dream llm-recluster [--threshold 25] [--out <path>]`. The actual application happens via `mem dream apply <plan-file>` after human review.

pub fn purge_invalidated(conn: &Connection, opts: PurgeOptions) -> MemStoreResult<PurgeReport> {
    let mut sql = String::from("WHERE valid_to IS NOT NULL");
    let mut binds: Vec<String> = vec![];
    if let Some(b) = &opts.before {
        sql.push_str(&format!(" AND datetime(valid_to) < datetime(?{})", binds.len()+1));
        binds.push(b.clone());
    }
    if let Some(r) = &opts.reason_filter {
        sql.push_str(&format!(" AND reason LIKE ?{}", binds.len()+1));
        binds.push(format!("%{}%", r));
    }

    let count_sql = format!("SELECT COUNT(*) FROM relations {}", sql);
    let count: u64 = {
        let mut stmt = conn.prepare(&count_sql)?;
        let bind_refs: Vec<&dyn rusqlite::ToSql> = binds.iter().map(|s| s as &dyn rusqlite::ToSql).collect();
        stmt.query_row(rusqlite::params_from_iter(bind_refs), |r| r.get::<_, i64>(0))? as u64
    };

    if !opts.dry_run && count > 0 {
        let del_sql = format!("DELETE FROM relations {}", sql);
        let bind_refs: Vec<&dyn rusqlite::ToSql> = binds.iter().map(|s| s as &dyn rusqlite::ToSql).collect();
        conn.execute(&del_sql, rusqlite::params_from_iter(bind_refs))?;
        crate::audit::record_purge(conn, count, opts.before.as_deref(), opts.reason_filter.as_deref(), &opts.actor)?;
    }

    Ok(PurgeReport { count, dry_run: opts.dry_run })
}

```rust
pub fn route(conn: &Connection, opts: RouteOptions) -> MemStoreResult<RouteReport> {
    let now = chrono::Utc::now().to_rfc3339();
    let tx = conn.unchecked_transaction()?;

    // 1. Find the existing direct edge to capture its rel_type and scope.
    let direct: Option<(String, String)> = tx.query_row(
        "SELECT relation_type, scope FROM relations
         WHERE from_id=?1 AND to_id=?2 AND valid_to IS NULL LIMIT 1",
        rusqlite::params![opts.from, opts.to],
        |r| Ok((r.get::<_, String>(0)?, r.get::<_, String>(1)?)),
    ).ok();

    let (orig_rel, scope) = direct.ok_or_else(||
        crate::error::MemStoreError::NotFound(format!("no active direct edge {}->{}", opts.from, opts.to)))?;

    let rel_in = opts.rel_in.unwrap_or_else(|| orig_rel.clone());
    let rel_out = opts.rel_out.unwrap_or(orig_rel.clone());

    // 2. Invalidate the direct edge.
    let direct_invalidated = tx.execute(
        "UPDATE relations SET valid_to=?1, reason=?2
         WHERE from_id=?3 AND to_id=?4 AND valid_to IS NULL",
        rusqlite::params![now, opts.reason, opts.from, opts.to],
    )? as u64;

    // 3. Create the two segments.
    tx.execute(
        "INSERT OR IGNORE INTO relations (from_id, relation_type, to_id, scope, valid_from, valid_to, confidence, properties_json, created_at, reason)
         VALUES (?1,?2,?3,?4,?5,NULL,1.0,'{}',?5,?6)",
        rusqlite::params![opts.from, rel_in, opts.via, scope, now, opts.reason],
    )?;
    tx.execute(
        "INSERT OR IGNORE INTO relations (from_id, relation_type, to_id, scope, valid_from, valid_to, confidence, properties_json, created_at, reason)
         VALUES (?1,?2,?3,?4,?5,NULL,1.0,'{}',?5,?6)",
        rusqlite::params![opts.via, rel_out, opts.to, scope, now, opts.reason],
    )?;

    tx.commit()?;
    Ok(RouteReport { direct_invalidated, edges_created: 2 })
}

pub struct Hub { pub id: String, pub degree: u32 }

pub fn find_hubs(conn: &Connection, threshold: u32) -> MemStoreResult<Vec<Hub>> {
    let mut stmt = conn.prepare(
        "SELECT id, COUNT(*) FROM (
            SELECT from_id AS id FROM relations WHERE valid_to IS NULL
            UNION ALL
            SELECT to_id AS id FROM relations WHERE valid_to IS NULL
         ) GROUP BY id HAVING COUNT(*) >= ?1 ORDER BY 2 DESC")?;

        Ok(Hub { id: r.get(0)?, degree: r.get::<_, i64>(1)? as u32 })

    let mut out = Vec::new();

    Ok(out)
}

pub fn apply(conn: &Connection, plan: &ClusterPlan) -> MemStoreResult<ApplyReport> {
    let mut applied = 0;
    let mut errors = Vec::new();
    for c in &plan.clusters {
        let opts = IntroduceTopicOptions {
            topic_id: c.topic_id.clone(),
            entity_type: c.entity_type.clone(),
            sources: c.sources.clone(),
            anchor: c.anchor.clone(),
            rel_source: c.rel_source.clone(),
            rel_anchor: c.rel_anchor.clone(),
            reason: c.reason.clone(),
        };
        match introduce_topic(conn, opts) {
            Ok(_) => applied += 1,
            Err(e) => errors.push(format!("cluster {}: {}", c.topic_id, e)),
        }
    }
    Ok(ApplyReport { clusters_applied: applied, errors })
}
