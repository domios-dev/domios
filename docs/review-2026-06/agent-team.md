# Agent Team Setup — Multi-Provider Onboarding & Model Routing

**Status:** PROPOSED — companion to [stabilization-backlog.md](stabilization-backlog.md).
Defines (1) how non-Claude coding agents get project instructions, (2) which model
tier executes which backlog task, and (3) how the arbiter dispatches.

---

## 1. The instruction-file gap (verified)

What each agent sees when opening this repo today:

| Agent | Looks for | Present? | Result |
|---|---|---|---|
| Claude Code | `CLAUDE.md` | yes (14K, comprehensive) | fully briefed |
| **OpenAI Codex / GPT** (the actual target — spawnable via `provider-codex`) | `AGENTS.md` | **no** | blind — every Codex worker lands with zero project rules |
`AGENTS.md` is OpenAI Codex's native instruction file — the cross-vendor agents.md
convention originated there; any future tool joining the team (Gemini etc.) reads it
as fallback, for free. This team is Claude Code + Codex; nothing else is in scope.
Claude Code reads `CLAUDE.md`. So the repo needs both, **without maintaining two divergent
rulebooks** — divergence here is exactly the doc-drift disease WS-B treats elsewhere.
The stakes are concrete: the routing rubric (§2) assigns real backlog tasks to
GPT-5.5/Codex Spark workers, and today those workers would execute them without
CLAUDE.md's hard rules (never touch prod 7685, no auto-commit, lock ordering, file-size
discipline). G1 is therefore a hard prerequisite for any non-Claude dispatch, not a
nice-to-have.

### Decision: AGENTS.md as a thin, generated mirror

Recommended (task G1 below): keep `CLAUDE.md` canonical (it's battle-tested and full
of Claude-specific delegation mechanics), and generate `AGENTS.md` from it:

1. `scripts/gen-agents-md.sh` copies CLAUDE.md → AGENTS.md, prepending a header:
   `<!-- GENERATED from CLAUDE.md — edit CLAUDE.md, run scripts/gen-agents-md.sh -->`
   and stripping/translating Claude-only sections (the `Agent(subagent_type=…)` spawn
   syntax gets a vendor-neutral equivalent; mem protocol references become inline
   instructions, since Codex workers have no mem harness rules of their own).
2. CI check (extends B7's `docs-source-of-truth.yml`): AGENTS.md stale vs CLAUDE.md →
   fail with "run the generator".
3. No vendor-specific extras beyond AGENTS.md — Codex reads it natively, and each
   extra format (`.cursor/`, `GEMINI.md`, …) is a second drift surface for a tool
   that isn't on this team.

Why not symlink? Windows + git symlinks are unreliable (this repo's primary dev box is
Windows). Why not make AGENTS.md canonical? CLAUDE.md contains Claude-harness-specific
mechanics (skills, mem ids, subagent_type) that would confuse other vendors if served
raw; the generator is the translation point.

> Note: the user-global rule "never edit AGENTS.md — auto-generated by CodeTerm"
> applies to the General Agent's *home-directory* instruction files that CodeTerm
> regenerates at runtime, NOT to this repo's checked-in source docs. The generator
> script must document this distinction in its header to avoid confusing future agents.

## 2. Model routing rubric

Four executor tiers are available to the arbiter. Assignment per task is in the
backlog header lines; this is the reasoning, so future tasks can be routed without
re-deriving it.

| Tier | Strengths | Weaknesses | Use for | Never use for |
|---|---|---|---|---|
| **Codex Spark** | fast, cheap, high-volume codegen | weak judgment on ambiguity; will "complete" a bad spec confidently | config boilerplate (lint configs, CI yaml), mechanical deletions with exact specs, fixture/scaffold generation, repetitive multi-file edits | anything with an open design question; security; tasks whose spec says "decide" |
| **Sonnet** | reliable spec-following, good code quality, cost-efficient | won't push back on a flawed task; limited cross-cutting view | well-specified bounded edits: doc syncs, small security patches with exact sites (F1), CLI fixes, test wiring, gitignore/hygiene | L-effort refactors; tasks requiring architecture decisions |
| **Opus** | strong reasoning, safe large refactors, catches spec errors | slower, costlier | god-file splits (A1, E3, F2), fixture/architecture design (D2, D5, E6), translation judgment (G1), anything where the task says "design" | bulk mechanical work (waste), trivial doc edits |
| **GPT-5.5** | strong generalist from a different model family; excellent long-doc synthesis; uncorrelated blind spots | not integrated with mem/skills harness conventions — needs AGENTS.md (G1) landed first | large doc synthesis (B3, D6), provider-pattern writeups (F3), **cross-family review**: adversarial second opinion on Opus designs before implementation | tasks depending on Claude-harness specifics (skills, mem ids) until G1 lands |

Routing heuristics:
1. **Effort × ambiguity decides the tier.** S-effort + exact file:line spec → Spark or
   Sonnet. Any task containing "decide/design/define" → Opus. Long-document
   reconciliation → GPT-5.5.
2. **Security and prod-adjacent always ≥ Sonnet** with verification steps in the task;
   never Spark.
3. **Cross-family review is cheap insurance:** Opus designs (D2, D5, E6, G1, B7) get a
   GPT-5.5 review pass before implementation — different-family models miss different
   things; same-family review re-confirms the same blind spots.
4. **Escalation rule:** an executor that hits an undocumented design decision STOPS and
   reports — the arbiter re-routes that slice up a tier. Never let Spark/Sonnet
   improvise architecture mid-task.
5. **Verification asymmetry:** it's fine for a cheaper tier to *verify* a more
   expensive tier's mechanical output (acceptance-criteria checks are spec-following),
   but design review only flows sideways (GPT-5.5) or up.

### How tiers are actually spawned (verified live, 2026-06-11)

Two dispatch modes, both verified against prod:

1. **Standing panes** (workspace `codeterm`): Opus `232c0b4a`, Sonnet `228012ad`,
   Haiku `35a191bc`, Spark `8b153ef9` (Codex), Gpt5.5 `a10ccdbd`. Dispatch:
   `codeterm send-text "<brief>" --pane <id>`. Return path: they reply with
   `codeterm send-text "…" --pane 5c64a651` (NOT `agent report` — they aren't
   hierarchy children of the arbiter, reports won't route).
2. **Ephemeral workers**: `codeterm agent spawn <provider> --model <m> --role Worker
   --parent 5c64a651 --workspace <ws> --cwd <path> --task "<brief + 'when done run:
   codeterm agent report …'>"`. Verified for claude (haiku), codex (gpt-5.5),
   opencode — full round trip including auto-routed reports. Model discovery:
   `codeterm agent providers`, `codeterm agent models <provider>`.

Verified model menu: claude = opus-4.7 / sonnet-4.6 / haiku-4.5; codex = gpt-5.5
(default) / 5.4 / 5.4-mini / 5.3-codex / 5.2; opencode = 7 models. Haiku joins the
rubric as a fifth tier: probes, single-fact verifications, acceptance-criteria
re-runs, S-effort doc edits — anything where speed beats depth.

Caveats that survive verification: (1) non-Claude workers don't have the mem
protocol or CodeTerm skill conventions in their harness — briefs must inline
everything (task texts in the backlog are self-contained for exactly this reason);
(2) GPT-5.5/Spark dispatch on repo tasks stays gated on G1 (AGENTS.md), otherwise
Codex workers operate without the hard rules; (3) invalid `--role` strings are
silently swallowed (C1) — until fixed, double-check `role=` in
`codeterm agent list --json` after every spawn.

## 3. Dispatch protocol (arbiter)

1. Dispatch by the backlog's wave table; within a wave, tasks are independent — run in
   parallel, one executor per task, isolated branches/worktrees.
2. Every brief = the task text verbatim + the "Rules for executors" header + the
   relevant companion doc section. Executors don't get the whole backlog (context
   discipline; CLAUDE.md: delegate, keep context cheap).
3. Reports come back against acceptance criteria with pasted command output (the
   testing-process §4 evidence standard applies to ALL tasks, not just tests).
4. Arbiter spot-verifies: re-run at least one acceptance command per completed task
   before marking done. Trust, then verify, in that order.
5. A completed wave updates this folder: check the task off in the backlog with a
   one-line outcome + commit hash. The backlog is the single progress ledger — no
   parallel TODO lists.
