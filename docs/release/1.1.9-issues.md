### #1 — CLI auth against local dev API rejects mesh-signed token (S4 SMOKE)

**Severity:** follow-up (NOT a blocker for #31 — pre-existing, predates Phase 2 splits)

**Reproduce:**
```bash
# From outside any CodeTerm tab (no $CODETERM_API_TOKEN set)
CODETERM_API_PORT=7686 codeterm mem save --kind fact --title T "body"
# → Error: Invalid or missing token (HTTP 401)
```

**What's happening:**
- `read_api_config()` token priority is: `$CODETERM_API_TOKEN > mesh_signed_token > config.toml api.token`.
- When called from outside a CodeTerm Tab, `$CODETERM_API_TOKEN` is unset.
- `read_mesh_signed_token()` reads `~/.codeterm-dev/mesh/identity.json` and produces a fresh Ed25519-signed token.
- The dev API's local auth (`check_auth` in `api/routes`) does NOT recognise the self-instance's mesh-signed token.
- Result: 401 `"Invalid or missing token"` text/plain body.

**Why it's not in master prod:**
- Prod (port 7685) accepts the same self-signed mesh token (200 OK on identical CLI call).
- Either prod's `check_auth` has a self-peer fallback that dev's lacks, or prod's mesh identity got registered as a peer-of-self at some point.
- Likely a runtime state difference, not a code regression.

**Why pre-existing:**
- The token-priority logic was set in commit b66999b (May 3, before Phase 2 split campaign on May 4). Phase 2 only moved the function from main.rs to cli/src/main.rs un-changed.

**Workaround for SMOKE testing:**
```bash
DEVTOK=$(awk -F'"' '/^token/{print $2}' ~/.codeterm-dev/config.toml)
CODETERM_API_PORT=7686 CODETERM_API_TOKEN="$DEVTOK" codeterm mem save ...
```

**Proposed fix (out of scope for #31):**
- For local-API calls (no `--mesh PEER`), prefer config.toml api.token over mesh-signed.
- Mesh-signed only when target is a remote peer.
- Server side: `check_auth` should accept the local instance_id's signed token as "self".

**Affects:** every CLI command that hits the local dev API from outside a Tab. Inside a Tab it's fine because PTY sets `$CODETERM_API_TOKEN` to the plain config token. SMOKE tests run from outside Tabs, so they hit this.

### #2 — CLI error messaging swallows non-JSON 4xx response bodies

**Severity:** quality-of-life — keeping the small fix, NOT a blocker

**Was:** `mem_post_request` did `let val = resp.json().unwrap_or_default();` — for 4xx with text/plain body, val became `Value::Null` and the error printed "Error: null".

**Action:** decide whether to land this small fix in #31 or split out. It's confined to `cli/src/cmd/mem.rs::mem_post_request` (lines 57-69), 3-line change, strict improvement.

### #3 — CLI defaults to first `codeterm-*` socket pipe found, leaks to prod

**Severity:** plan-bug + follow-up — patched test plan setup; CLI behavior is pre-existing

**What happened:**
- `discover_socket()` (cli/src/client.rs:127) scans the pipe directory for the
  first entry matching `codeterm-*`. On Windows that's `\\.\pipe\codeterm-{PID}`
  (prod, started first) before `\\.\pipe\codeterm-dev.sock` (dev).
- HTTP-routed CLI commands (`mem`, `mesh peers`, `bridge`) use `read_api_config()`
  which respects `CODETERM_API_PORT=7686` → hit dev correctly.
- Socket-routed CLI commands (`workspace`, `tab`, `agent.spawn`, `send`,
  `cron`) use `discover_socket()` which finds prod's pipe first → silently hit prod.

**Effect during BLACKSTAR SMOKE:**
- S3 (workspace create), S5 (cron create), S6 (agent spawn), S7 (send)
  all landed in prod, not dev. Andrey caught this — visible in prod sidebar
  as "test-ws / Test Orch" alongside real prod workspaces.

**Fix in the test plan:** require `CODETERM_SOCKET_PATH` alongside
`CODETERM_API_PORT` + `CODETERM_API_TOKEN`. Setup section now spells out
all three env vars and adds a verification step (`codeterm workspace list`
must show only dev workspaces before SMOKE starts).

**Proposed CLI fix (out of scope for #31):**
- `read_api_config()` already does port/data-dir resolution based on
  `CODETERM_API_PORT == 7686` (returns `.codeterm-dev` data dir name).
- `discover_socket()` could grow the same fallback: if `CODETERM_API_PORT=7686`
  and `CODETERM_SOCKET_PATH` is unset, prefer `codeterm-dev.sock` over
  `codeterm-{PID}.sock`. One-line addition, eliminates silent leak.

**Affects:** anyone running CLI tests against dev without setting all three vars.

### #4 — mem WAL not truncated through SIGTERM + reopen cycle (Mac DETAILED A2)

**Severity:** follow-up — cross-confirmed by BLACKSTAR; benign per SQLite default behavior, NOT a #31 blocker

**Reproduce:**
```bash
ls -la ~/.codeterm-dev/mem/knowledge.db-wal
# pre-shutdown:  ~4MB
kill -TERM <dev-daemon-PID>
ls -la ~/.codeterm-dev/mem/knowledge.db-wal
# post-shutdown: ~4MB — unchanged
pnpm tauri dev
ls -la ~/.codeterm-dev/mem/knowledge.db-wal
# post-restart:  ~4MB — still unchanged
```

**Cross-peer observation (consistent → deterministic, not a flake):**
- Mac: 4,120,032 bytes
- BLACKSTAR: 4,499,072 bytes

**What's expected:** test plan A says "Quit (Cmd+Q) — clean shutdown, mem WAL checkpointed (`.db-wal`: no file or small)". Got 4MB WAL surviving through full kill+restart on both peers.

**Why it's benign:**
- SQLite WAL auto-checkpoint default threshold is ~1000 pages (~4MB at 4KB pages) — both observed sizes line up exactly with a single auto-checkpoint window
- WAL pages re-apply cleanly on next open, no data loss, Tabs auto-resume normally
- A2 expectation was overly strict — "small or absent" should read "DB readable + auto-resume works", which both peers confirm

**Proposed fix (out of scope for #31):** wire `PRAGMA wal_checkpoint(TRUNCATE)` into the mem-store shutdown hook. One-line change in startup/teardown.

### #8 — `mesh disconnect <name>` silently no-ops; requires UUID instance_id

**Severity:** follow-up — pre-existing (predates Phase 2), not a #31 blocker. Documented + workaround applied.

**Reproduce:**
```bash
codeterm mesh peers
# Paired:
#   ● Andreys-MacBook-Air-5 (100.85.116.96)

codeterm mesh disconnect Andreys-MacBook-Air-5
# stdout: "Disconnected from Andreys-MacBook-Air-5"   ← lies
# exit:    0                                           ← lies

codeterm mesh peers
# Still paired. peers.json unchanged on disk.
```

**Root cause:** CLI passes user-supplied arg as `instance_id` field in the POST
body verbatim. API's `mesh_disconnect_peer` (mesh_routes/connection.rs:182)
reads it, then `state.mesh.lock().unpair(&instance_id)` runs. `unpair()`
(mesh/mod.rs:152) does `self.paired_peers.remove(instance_id)` — keyed by UUID,
not name. Returns None for any non-UUID lookup. No save, no log, no error.

The "Disconnected from X" info-log on connection.rs:242 fires unconditionally
AFTER unpair returns, regardless of whether unpair actually found anything.

**Workaround:** disconnect by UUID, not name:
```bash
codeterm mesh peers --json | python -c \
  "import json,sys;[print(p['instance_id']) for p in json.load(sys.stdin).get('paired',[]) if p['instance_name']=='Andreys-MacBook-Air-5']"
codeterm mesh disconnect 7d55b9a5-facd-46a2-9dbd-d7e47da79ffa
# Logs now show "[mesh] Unpaired 7d55b9a5-..." and peers.json updates.
```

**Proposed fix (out of scope for #31):**
- CLI side: in cmd/mesh.rs `MeshAction::Disconnect`, if the arg doesn't parse
  as UUID, resolve via `mesh peers` lookup before sending.
- OR API side: accept either UUID or name in `mesh_disconnect_peer`'s body —
  if name, look up the UUID server-side.
- Either fixes the silent-success surface area.

**Affects:** every disconnect path that takes a human-typed name. Users
typically discover peer names from `mesh peers` output and naturally type
those, not the UUIDs. Test plan J Step 1 example also uses name.

**Test plan delta:** J Step 1 should specify "use UUID not name (issue #8)".
Patch in same commit as this entry.

### #9 — Asymmetric peer-address registration after dev re-pair

**Severity:** follow-up — routing still works, but address record diverges between peers

**Observed during J Step 4-6:**
- Mac side: BLACKSTAR registered with `addr=100.84.159.37` (Tailscale)
- BLACKSTAR side: Mac registered with `addr=192.168.1.173` (LAN, mismatched subnet)
- Both report `online=true`, mesh-routed send Step 5 round-trips successfully.

Likely cause: each side records the address it OBSERVED the inbound pair packet
arriving from. Mac observed BLACKSTAR's connect request via Tailscale (because
that's how the broadcast made it across subnets); BLACKSTAR's own discover
phase had picked up Mac's UDP broadcast tagged with his LAN IP, and used that
for the outbound connect.

**Why it's not a J blocker:** Step 5 succeeded — mesh-routed send from
Mac to BLACKSTAR Tab 7e21e6f5 landed correctly with the `[Mesh: ...]` prefix.
Routing handled the address mismatch (probably via Tailscale MagicDNS routing
LAN-IP packets through Tailscale subnet routes, or the relay path resolves
peer by instance_id and walks the address list).

**Why it's worth a fix:** if the LAN address goes stale (Mac's router DHCP
rotates 192.168.1.173 to a different host), BLACKSTAR's outbound mesh calls
will route to the wrong host until next discovery refresh. Plus the asymmetry
makes the `addresses` field in `peers.json` confusing for debugging.

**Proposed fix (out of scope for #31):** during pair-confirm, normalize the
peer address to the Tailscale interface if both sides share Tailscale (which
they always do for cross-subnet peers). Or: pair-confirm exchanges the FULL
`addresses` array including all known interfaces, both sides then dedupe.
