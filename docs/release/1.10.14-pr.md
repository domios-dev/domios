## How to use this file

- A slice that **fixes** an issue adds one `Repository-Issue:` line under "Fixed" when its lane
  merges into `develop`. GitHub ignores closing keywords on PRs that do not target the default
  branch, which is why the intermediate form is metadata and not a closing keyword.
- A slice that only **investigates** an issue uses `Refs`, never a closing keyword. Referencing an
  issue you did not fix is worse than not referencing it at all.
- Anywhere else in this file, write an issue number inside backticks. The renderer rejects a bare
  hash-number in prose so that no reference can silently skip the metadata contract.
- Before opening the final `develop` -> `master` PR, render the closing block:

  ```bash
  python3 scripts/release_issue_contract.py repository-closes --body-file docs/release/1.10.14-pr.md
  ```

  Put the emitted closing lines in the master PR body. Do not hand-write them.
- Public `codeterm-releases` issues stay separate `Public-Issue:` metadata and close only after
  verified artifact publication. See `docs/RELEASE.md`.

## What this release is about

Two defect families, both a form of the same failure: a surface reporting a state it did not observe.

1. **Dishonest success.** Crash-restore reports "all N panes restored" while a pane comes back a
   bare shell. Provider exit leaves a tab `agent_ready`. A model-availability probe that could not
   run is cached as a definite "unavailable". A hand-placed closure boundary is trusted on presence.
2. **Ungated or divergent surfaces.** Report cards render on top of the loading spinner. CLI and UI
   derive agent state from different signals. The mesh panel counts peers the CLI does not.

### Orchestrator, Worker and Planner prompts: coordination and reports carry evidence, not ceremony (no issue — field incidents)

Two Orchestrators on one machine failed in mirror image on the same day: one ran the full canonical
gate nine times for one-line repairs; the other gated diagnostic runs behind review and sent
roughly twenty-five ledger demands for runs that were never release evidence. A third Orchestrator
hit the lane-dispatch refusal the LANES doc said could not happen. Each is now a rule rather than
an anecdote, and each rule is one to three sentences. Orchestrator: a message is sent only when it
carries a decision, evidence or a state change; a diagnostic run is reviewed after, never before;
one bounce per failure class, never per symptom. Worker: proven and inferred are separated by name,
and a PASS that names a required repair is a bounce. Planner: a task is overhead justified against
a closed list of boundaries, not the default container for work. `docs/LANES.md` now says the
dispatcher does not auto-provision a lane, with the sequence that works. Prompt mechanism tests: 44
passed.

### Orchestrator prompt: the two verification tiers are not interchangeable (no issue — field incident)

An Orchestrator on another plan ran the full canonical regression gate (15-35 min, Docker + PostgreSQL,
one lease per machine) **nine times for three releases** — five on intermediate candidates, three of
them reruns to prove a one-line repair a thirty-second focused check would have settled. A peer
protocol between two Orchestrators had extended into forbidding focused checks before review, so the
first executable check on a fourteen-file merge was the full gate and every trivial defect cost a
full run.

The rule existed and was not operational: "run it once at final integration or release verification"
reads as *per merge*. The prompt now separates the tiers explicitly — a focused check proves one
change and is never skipped because a broader gate is coming; a broad gate proves a release, runs on
the release SHA once, and is never a repair's first executable check. It also names the override that
actually happened: a peer protocol may serialize a shared machine resource but may not forbid the
focused checks that keep the broad gate down to one run. Two broad-gate runs with no release between
them is the stop signal.

### Mesh: one store, one projection, one answer (`task_tlnlka`, lane tip `bfb6bd5`)

paired_peers could hold a live record and a dead duplicate under one instance_name after a peer re-minted its instance_id, so name resolution depended on HashMap iteration order and services were attributed to an id no rendered node used.
