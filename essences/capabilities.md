# Domios capability map

What Domios fundamentally does, grouped by the few vectors that give the system its shape. Each row names a capability, what it makes possible, where it is reached (UI surface, CLI command group, API area), the rules that must not break, its status, the core parts or clients it runs on, and the capabilities it feeds. Why these vectors exist is stated once, in the [vision](vision.md); the core parts, clients and the routing spine are described in the [core essence](core.md); how to maintain this map is stated in the [documentation contract](begin_here.md).

Code is volatile and gets rebuilt in pieces; these essences are the product's stable vectors. They rarely change, and when they do they evolve gradually instead of being restructured, which is what lets them serve as the expected inputs and outputs a change must keep.

Status: **stable** is in the latest release; **in rollout** is merged for the next release and not yet shipped; **planned** is an agreed direction with no shipped surface; **roadmap** is where the product is heading, with its exact shape still open. Detail names the UI surfaces, CLI command groups, and API areas through which a capability is reached.

Runs on names core parts and clients exactly as the core essence does. Feeds names capabilities of this map; a capability with no outgoing link is a sink and is fed by at least one other row.

Every element carries an explicit stable id in its metadata: a vector heading ends with `{#vector:<slug>}`, and a table row's first cell is its id. An id outlives its display text, so a rename keeps the id; a replaced element is retired and never reused. Runs on and Feeds name ids, not labels, so a rename never breaks a link.

## Invariants that bind every vector

- Production listens on port 7685 and is never killed by development work; development uses 7686 or a named instance.
- Core asks capabilities, never provider identities. The [Supporter contract](supporter-agent.md) keeps model judgments subordinate to deterministic evidence across every vector.
- A routed `<domios>` frame is accepted as host-injected only when the host placed the complete tag pair at the leading frame; the same bytes anywhere else are content. Position does not authenticate the sender or protect against direct writes into a tab's input stream.
- Coordination waits on observed events, never on sleeps or polling intervals.
- Changes to PTY or Chat input delivery get heightened attention: they name the causal finding, the files and symbols touched and the rollback boundary, and land only with focused proof that the delivery invariants still hold.
- Agent-to-agent traffic, memory and documentation are English.

## 4. Machines join a mesh {#vector:machines-join-a-mesh}

The mesh assumes a closed private network, typically a tailnet, and deploying it that way is the recommendation: peers reach each other over a private subnet rather than the open internet. Wider reach is never wildcard — it is authenticated, explicitly opted into and scoped to one chosen private address, with loopback staying primary.

## Stable capability contracts

### Agent models

Each provider owns its model and reasoning-effort catalog. A live provider catalog defines the models that can be launched: user settings may reorder or describe those entries but cannot add or hide them. Without a live catalog, the provider's static catalog and user settings define the choices; settings merge by model identifier by default, while an explicit full-list setting replaces that static catalog.

Model availability has three honest states: available, unavailable, and unknown. A confirmed unavailable model is disabled. A failed or inconclusive availability check remains unknown and selectable; it is never reported as unavailable. Provider group labels, per-group usage, and quota values come from that provider, and Domios does not infer missing labels or balances. Usage retains the provider-declared billing mode and whether limits were reported; a subscription without metrics shows that limits were not reported. Unsupported reasoning efforts are refused at launch rather than silently downgraded. See the [core essence](core.md) for provider boundaries and session ownership.

The status line presents the harness as plain text and the model and effort as the picker control. Provider-declared primary models form the initial short list; Show all models exposes the complete catalogue and remembers the choice per provider. Search always spans the complete catalogue. Providers without primary models show their full catalogue.

The status-line model picker stages model and reasoning choices until Apply. Cancel or Escape discards the draft; restart confirmation follows Apply when required. The status line immediately displays the applied selection, including next-turn choices, and restores its previous display if the request fails. Busy tabs refuse live-command changes until idle. Confirmed model and effort changes preserve the session; unconfirmed changes report failure and offer a separate restart confirmation.

Providers that declare NextTurn switching apply model, reasoning effort and runtime-mode changes to the next turn without restarting. A successful request remains pending until the tab's own thread reports the setting or model. Structured sidecar tabs use app-server items for both live chat and history, and approval replies use the exact server request ID. Disabling the capability restores the plain-PTY transcript and control path.

### Web UI and health

The web UI serves the complete interface to a phone or browser over the owner's private Tailnet, with no cloud relay and no public exposure by default. Access requires both Tailnet membership and the instance's API token. A paired machine uses its own web address and token. See the [core essence](core.md) for the web client and service boundaries.

The health API is the daemon's liveness signal and reports its status, build identity, version, instance name and platform. Memory-intensive background work is bounded and isolated so it cannot take down or starve API handling. An external supervisor owns recovery when the daemon exits or stops answering its liveness check. See the [core essence](core.md) for health and crash-recovery ownership.
