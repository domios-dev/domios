# Independent frontend release

`frontend-release-contract.json` owns the version and API range of the next `frontend-vX.Y.Z` release; increment it before each one. Every app embeds a frontend of its own app version. An app accepts only a compatible release strictly newer than its rendered frontend, retires stored releases that are not newer than its own version or are incompatible with its API on start, and never offers an older or incompatible release, so an app update never runs an older downloaded UI. A frontend release therefore reaches only apps older than its version. `GET /api/frontend/status` names the rendered frontend under `rendered` (`releaseId` null for the embedded one). Contract version 1 uses exactly six manifest fields, sorted compact UTF-8 JSON without a newline. SHA256 covers the archive. Detached default prehashed minisign (`ED`, Ed25519 over BLAKE2b-512) covers the entire manifest. Format reference: https://jedisct1.github.io/minisign/.

Archive entries are UTF-8 byte sorted regular files, USTAR, mode 0644, uid/gid/mtime zero, no owner names, gzip level 9 without wall-clock metadata. Symlinks and nonregular files are refused. Entries have no wrapping dist directory. Paths longer than 100 UTF-8 bytes are refused explicitly.

Fixtures: `fixtures/frontend-test.pub`, `frontend-test.pem`, `frontend-manifest.json`, `frontend-manifest.json.minisig`, `frontend-v1.0.0.tar.gz`, and `dist/`. This is an intentionally public TEST ONLY key pair. Runtime tests inject this public key; production must never bake it in. The committed archive contains index.html and assets/fixture.js. Producer verification uses Node crypto; the consumer's independent minisign-verify implementation must also accept the fixture after merge.

Production uses the dedicated frontend minisign key BFA7F533AE232104: its public key is in this contract and the baked daemon/app constant, its private half is the FRONTEND_SIGNING_PRIVATE_KEY secret of the release environment (backup in the Domios secret store as domios-frontend-signing-key), and publication uses the GH_RELEASE_TOKEN in the release environment. The release environment deploys only from release/* branches and requires reviewer rollacode. Both jobs also require the rollacode actor. Both jobs run on any free light Linux runner; the build job uses an installed minisign or fetches minisign 0.12 and checks its pinned SHA256. The secret is an unencrypted minisign key protected by the GitHub environment; it is passed via environment, written to a mode-0600 temporary file, never put in argv or logs, and deleted in finally. The publication token needs only Contents write on rollacode/codeterm-releases. Neither job uses the app updater key. Build has only source Contents read; publication has no signing secret.

The owner must create the separate frontend-latest discovery release once with latest=false; it must not change app latest. Publication creates a new version draft, uploads all immutable assets without clobber, reads each asset back byte-for-byte, publishes with latest=false, then updates the discovery manifest and detached signature. Old versioned releases remain downloadable. Partial failures leave an unpublished draft for owner review; reruns refuse existing versions. Discovery asset pair replacement is not atomic on GitHub: during replacement a verifier can see mismatched bytes and must fail closed, retaining its active bundle. A discovery failure after version publication leaves the old discovery available; recovery updates discovery only after re-verifying complete version assets. No version asset is overwritten.

The workflow runs only when release.yml calls it for a frontend-only release or by manual dispatch; pull requests no longer run it. A dry run takes the tag from committed frontend metadata, signs with the committed TEST key, uses a read-only source token and skips the publication job.
