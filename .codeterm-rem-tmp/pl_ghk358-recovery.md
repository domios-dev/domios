### sec_zb6lvx — "Success criteria & correctness vector"

A submission is only reported successful when:
1. **Echo evidence**: either the literal text (normalized-whitespace substring or suffix-match for ≥1024-byte pastes, inject_verify.rs:161-188) or the paste-placeholder (`[Pasted text #N(+M lines)]`) is observed on screen, OR (when `verify_echo=false`) at least one screen-activity generation tick is observed after paste (`wait_for_paste_activity`) — never a blind no-op.

**Required properties (WHAT):**
1. **Fail-closed:** a relay that reports any error has written NOTHING to the target PTY — error taxonomy and the write must be ordered so bytes-after-404 is structurally impossible.

5. **Action transport:** `--actions enter` delivers a keypress at the target, never an empty stamped message.

### sec_0gi9oc — "Acceptance model: bytes-written vs provider-accepted"

**Delivery has FOUR distinct states, and conflating any two of them is how this plan's bugs keep shipping:**
1. `bytes_written` — the PTY write syscall succeeded (transport ack; what optimistic delivery reports).
2. `echo_observed` — the text (or a paste placeholder) appeared on the target screen (screen scrape; unreliable per sub-defects 1-3 in sec_gnk2xm).
3. `submit_observed` — post-Enter screen evidence (drain/prompt/hash; screen scrape again).
4. `provider_accepted` — the provider ITSELF recorded the message as input: the user turn exists in the provider's own session store (Claude/Codex session JSONL — ground truth, transport- and render-independent), or an equivalent provider-native acknowledgement.

**Live evidence (prod 31f335d48, user repro):** Chat UI send to a Codex tab → send reported ok (state 1) → text parked UNSENT in the Codex composer (state 4 false, and even state 3 false). Optimistic write must never be read as acceptance; the plan's guarantee closes only on state 4 observability.

**Candidate regression mechanism (confirm in repro task):** the pre-9dbcda652 verify loop doubled as the ENTER RETRY engine — codex/opencode swallow `\r` during paste ingestion (send.rs:275 comment), and the loop's second Enter is what actually landed those sends. Softening the veto disarmed the retry: the swallowed Enter is now final, and silent.

**Required seam (WHAT):** a per-provider acceptance observable + deterministic retry protocol, testable end-to-end:
- Provider capability (trait-level, capability not identity per architecture rules): `acceptance evidence for delivery X` — session-store user-turn match where a session file exists (Claude/Codex), structural composer-empty+transcript-present fingerprint as fallback; `None` = honest unknown.
- A queryable delivery record: send returns a delivery id; `delivery_state(tab, id)` exposes states 1-4 so CLI/REST/Playwright/pytest assert acceptance uniformly (the stub-agent fixture implements the same seam deterministically).
- Deterministic retry protocol keyed on the acceptance observable, NOT on screen scrape alone: unaccepted-after-bounded-deadline → re-Enter (bounded attempts, idempotent via the composer still holding the text) → still unaccepted → surface a visible failure state on the tab/message (never silent). Optimistic transport ack stays; acceptance tracking rides on top.
