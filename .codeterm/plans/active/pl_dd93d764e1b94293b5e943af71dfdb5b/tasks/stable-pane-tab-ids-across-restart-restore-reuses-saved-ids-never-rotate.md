USER DIRECTIVE (round-102, born from a live incident): after a daemon restart + session restore, tabs/panes must come back with THE SAME ids they had — ids must be SAVED and REUSED, not regenerated. THE INCIDENT THAT PROVES THE COST: today's prod restart rotated every pane id; the plan owner binding, the planner hierarchy link, the planner_ref, in-flight sends, and delayed messages all pointed at dead ids — ownership needed re-claiming, the planner needed re-binding, a send bounced, and the watchdog/reconcile view briefly saw universal pane-gone. Every one of those repairs exists only because identity is not durable. DESIGN: (1) the session store already persists pane records — ensure pane_id AND tab_id (and workspace id) are saved verbatim and the restore path REUSES them when materializing panes instead of minting new ones; (2) collision rule: if a saved id is somehow already live (partial restart, double restore), the restore REFUSES to duplicate — keeps the live pane and logs, never silently forks identity; (3) everything downstream keys on ids staying stable: plan lane assigned_pane_id, hierarchy parent/child edges, planner_ref, mesh peer references to our panes, delayed-message targets — with stable ids these survive restarts with ZERO repair; add a restart drill asserting exactly that (bindings valid before == valid after, no reconcile drift generated by a clean restart); (4) mesh: remote peers cache our pane ids — stable ids make those caches survive our restarts (note in the drill); (5) the restore-matrix eval (evals/restore-matrix/) extends with an id-identity oracle: restored pane ids == pre-kill ids, per provider. SEQUENCING: POST-RELEASE deliberately — this rewires the restore path that FINAL STAGING and the release walkthrough depend on; do not destabilize restore during the endgame. The current release ships with the self-healing repairs (ownership re-claim etc.) which today's incident proved work.
