PROFILED LIVE (round-85, prod daemon at 286% CPU, machine unusable with 5 streaming agents; sample leaf profile: vt100::Row::write_contents 341, _platform_memmove 364, from_utf8 251, SpecFromElem::from_elem 209 — plus a separate sqlite/rename/stat cluster, see FOLLOWUP). ROOT CAUSE (present on the branch too — the release does NOT cure it): src-tauri/src/service/output.rs:150-160 process_pty_output calls screen_state.get_content_hash(pty_id, exclude_rows) on EVERY chunk; the hash serializes the FULL vt100 screen. 5 agents x ~50 chunks/s = full-screen serialization 50x/s, O(rows x cols) each. The hash feeds agent_tracker.update_output (status/activity detection) which does NOT need per-chunk granularity — human-visible status needs ~100-200ms resolution at most. FIX (implemented in lane/9be1c1-hash-debounce by Planner-as-worker): per-pty debounce on the content hash — if the last hash for this pty is fresher than HASH_DEBOUNCE_MS (150ms), skip serialization and reuse the cached decision; a trailing re-hash fires on the next chunk after the window so a burst's FINAL state is always hashed (no stuck-status regression — the wake/idle detectors read the settled screen). Config-free constant, justified: below human perception, 30x reduction under load, zero behavior change beyond latency <150ms on status flips. FOLLOWUP LEAD (second cluster, separate lane): sqlite3VdbeExec 295 + rename 302 + open 281 + stat 310 — something does atomic-file/sqlite writes at chunk-ish cadence (suspects: output persistence, session store, usage_activity.mark); profile after this fix lands and file separately if it holds.
