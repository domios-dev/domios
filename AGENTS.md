# CodeTerm

**OS for AI agents.** Cross-platform terminal multiplexer where AI agents live, work, and coordinate. Tauri v2 (Rust) + React/TypeScript + xterm.js. Full vision: `VISION.md`.

## Hard rules

- **English only** in code, comments, commit messages.
- **No external user base yet** — this is Andrey's personal project. No backward-compat shims, no migration paths. Breaking changes are fine. Delete legacy aggressively. When in doubt, rewrite rather than patch.
- **Never kill prod CodeTerm.** Prod = port 7685, dev = port 7686. See *Process safety* below.
- **Hot-reload over restart.** Subsystems should support stop/start without restarting the whole daemon when possible.
- **Windows reserved names are forbidden.** Never create a file or directory named `NUL` (or another Windows device name). Use ordinary temporary filenames instead; remove any accidental reserved-name artifact immediately with an extended `\\?\` path.

## Source file size discipline

**NEVER ship a source file over 1200 lines. Ever.** (`.rs`, `.ts`, `.tsx`, `.py`, `.swift`). This is absolute and has NO allowlist — an oversized file is a bug to fix by splitting, full stop, never to baseline away. Every code file is watched; there is no escape hatch. When a file approaches the limit, split by responsibility. If a single concern legitimately needs more than 1200 lines, your concern is two concerns wearing a trenchcoat.

- `mod.rs` files target <800 lines — facade + light glue. Heavy logic belongs in concrete files inside the module.
- Excluded: `target/`, `node_modules/`, `dist/`, `gen/`, `references/`, `vendor/`, `src-tauri/pty-fork/`, `.claude/`, data formats.
- Enforcement: `scripts/check-file-sizes.sh` (CI-wired, `--fail` mode). No allowlist file: if the check flags a file, split it.

When splitting a file with inline `#[cfg(test)] mod tests`, keep `mod tests;` in source and move the body to `<name>/tests.rs`.

## Build, run, test

Use `build.sh` (`build.ps1` from PowerShell). It scopes lifecycle operations to dev and never kills prod.

Choose the operation before running a command: shared development is `docs/BUILD.md#development`; a local production installer for this machine is `docs/BUILD.md#local-production-build-and-self-install`; public publishing is `docs/RELEASE.md`. Do not substitute one for another. For every newly discovered build failure, fix the owning step and add the symptom, cause, and recovery to that operation's troubleshooting section before declaring it complete.

```bash
./build.sh dev              # incremental dev (port 7686, hot reload, auto-builds CLI)
./build.sh check            # cargo check (~2s incremental)
./build.sh worktree-check   # canonical-only integration compile check
./build.sh test-one app NAME # one focused capped app test (pty/cli also supported)
./build.sh test-one plan NAME # one focused capped codeterm-plan test
./build.sh release-preflight # refresh and verify both Cargo lockfiles before a production build
./build.sh test             # Rust unit tests
./build.sh verify           # check + unit tests + source-size gate
./build.sh build            # production build
./build.sh install-local    # incremental production build + self-install (Windows canonical)
./build.sh cli              # rebuild CLI only → active ~/.codeterm-dev*/bin/
./build.sh kill             # safe kill of dev only
./build.sh e2e              # API E2E tests against running dev
source build.sh env         # load MSVC env into shell (Windows, manual cargo)
```

On macOS, local self-reinstall is built into the CLI, not a standalone script
or `build.sh install-local`. After `./build.sh build`, run:

```bash
codeterm update install --from-file "/path/to/CodeTerm.app" \
  --continue-tab "$CODETERM_TAB_ID" \
  --continue-prompt "Resume the interrupted task and verify the installed build."
```

The implementation lives in `cli/src/cmd/install.rs`. It replaces the app,
relaunches CodeTerm, and resumes the calling tab. Do not manually replace the
bundle or conclude that macOS self-install is missing because
`./build.sh install-local` is Windows-only.

`dev --wait` is automation-only; interactive verification uses one visible foreground dev tab. Run Rust tests only through `scripts/test-capped.sh`, one focused test at a time. Every build, test, dev run, and executable gate runs only from the canonical integration checkout under Orchestrator authority.

Isolated Worker lanes are source-only. They may inspect, edit, statically review, and commit owned source, but they never invoke `build.ps1`/`build.sh`, Cargo, project tests, dev servers, packaging, or validation gates, including focused checks. Workers author coverage and report exact deferred commands. After a real ancestry-preserving merge, the Orchestrator runs those commands in canonical. The only exception is a Worker assigned to canonical and given explicit permission for the exact gate.

Parallel writers always use separate worktrees/lanes; the canonical checkout has one writer/integrator at a time. This keeps commits atomic and allows ordinary `git add -A` inside a lane instead of fragile cross-owner file lists.

Gateway-backed build commands fail fast when the machine slot is busy. Report the returned blocker and continue source-only work; never poll or retry it. Use `--wait-build` only when blocking the caller is explicitly intended.

If foreground dev owns the gateway, canonical QA reports the conflict and waits
for an explicit integration decision. Never move the check into a lane, compose
a private `CARGO_TARGET_DIR`, or wait behind dev.

Use `./build.sh help` and the named build operations. Do not hand-compose Cargo manifests, packages, profiles, or gateway commands when a build operation already owns that intent.

## Build speed (worktrees, tests, profiles)

- Keep machine-level `sccache`; never share `CARGO_TARGET_DIR` across worktrees.
- Do not remove the tuned Cargo profiles.
- In canonical QA, use focused capped tests; a 90s timeout is a defect signal, not a reason to raise the cap.
- Reclaim stale targets with `cargo sweep --time 2` between efforts.

## Lane integration preserves ancestry

Never cherry-pick, squash, replay, or patch-copy work out of a worktree lane. Merge the lane branch with a real merge commit, and delete it only after `git merge-base --is-ancestor <lane-tip> <target-tip>` succeeds.

The pre-push hook is intentionally light on `lane/*` and full on integration branches. Do not add compilation back to lane pushes.

Interactive dev uses one visible foreground tab. Confirm 7686 is free, then:

```bash
./build.sh kill
codeterm tab new --cmd "cd $(pwd) && ./build.sh dev"
```

On PowerShell use `Set-Location '<checkout>'; .\build.ps1 dev`. Verify `/api/health` build SHA and a responsive window. A second Cargo/build owner is a failure.

**Before debugging, always verify the running build matches your code:**

```bash
curl -s http://127.0.0.1:7686/api/health | jq '.build'
```

If `build` (git commit hash) differs from `git rev-parse HEAD`, the old build is still running — restart with `./build.sh dev`. During iterative work the hash stays the same across restarts, so the real "did the restart take" signal is `./build.sh kill` (which guarantees the old process is gone) followed by a fresh `./build.sh dev`.

Dev logs: `~/.codeterm-dev/logs/codeterm.log`. Live tail: `tail -f ~/.codeterm-dev/logs/codeterm.log`.

Full testing guide: `docs/TESTING.md`; authoring contract: `docs/contributing/test-authoring.md`.

## Bench safety: NEVER call raw `codeterm` against dev — use the lib

Benches may inherit prod connection variables from their parent CodeTerm tab.
A bare `codeterm` call can therefore mutate prod instead of dev.

**Always** source the bench lib first and use its `dc` wrapper:

```bash
source "$(git rev-parse --show-toplevel)/evals/_lib/lib.sh"
dc workspace list           # locked to dev — fails with exit 7 if dev is down
dc --as-tab "$CODETERM_TAB_ID" plan create --title "smoke" # preserve an explicit dev caller
```

Sourcing the lib auto-calls `dev_env` (port 7686 + dev token + dev
socket pipe). The `dc` function asserts dev is alive on every call
before invoking the CLI, and re-exports the dev env-vars into the
CLI's process so a leaked parent var can't override it. HTTP
helpers in the lib (`dev_get`, `dev_post`) are hardcoded to
`http://127.0.0.1:7686` for the same reason.

Hard rule: **no bench script under `evals/` may invoke `codeterm`
directly.** Use `dc`. If you really need a prod-targeted CLI call,
do it explicitly outside the bench machinery, after a clear
"this is prod" log line — never inside an automated drill.

## Lock ordering (deadlock prevention)

Acquire in order, drop before awaiting. parking_lot is **not reentrant** — `mux.lock()` inside `mux.lock()` deadlocks.

1. `mux` (MultiplexerState)
2. `output_buf` (OutputBuffer)
3. `screen_state` (ScreenState)
4. `agent_tracker` (TabStatusTracker)
5. `pty` (PtyManager)

After parallel Rust refactors, grep for nested `.lock()` to verify ordering.

`clippy::await_holding_lock` is **DENIED** at the full gate — never hold a `std`/parking_lot guard across `.await`; extract the data and drop the guard first (scope it in a `{ }` or `let x = guard.field.clone();`), never silence with `-A`. The five ordered locks are wrapped in `lock_hold::{TimedMutex,TimedRwLock}`: debug builds log `[LOCK-HOLD] <name>.<op>() held Nms` past 50ms (`lock_hold::LOCK_HOLD_THRESHOLD`); release compiles to a transparent zero-overhead parking_lot wrapper.

## Async runtime & hot-path discipline (perf — learned the hard way)

Blocking/heavy work on the Tauri async runtime starves ALL IPC and freezes the WHOLE UI (every tab + sidebar), not just the caller. A 3-4s full-UI freeze on every tab switch was `plugin_manager_snapshot` forking CLI subprocesses (including a network `channel diff`) on the async runtime.

- **The daemon NEVER shells out to its own `codeterm` CLI.** Call the in-process function. A daemon forking its own CLI that reconnects to it is an architecture smell — and slow (process start + IPC + network per call).
- **Blocking / IO / heavy / subprocess work in a Tauri command → `tokio::task::spawn_blocking`.** Synchronous `dispatch::dispatch`, disk reads, network, `Command::new` all qualify. A plain sync `fn` command runs on the runtime too — same rule applies.
- **Hot-path commands (fire on tab switch / mount / render) must be cheap and bounded.** Cache expensive snapshots; rebuild on change (file-watcher / explicit action), never on every call.
- **Measure before optimizing.** The dev build logs `[SLOW-IPC] <cmd> <ms>` + `[LONGTASK]` (frontend `invoke` wrapper → dev log). A trivial command (e.g. `get_config`) blocking seconds means the runtime is starved; the slow command that resolves FIRST is the cause, the rest are queued victims — don't chase the victims. Test under realistic load (many tabs), not a clean 2-tab dev instance.
- **Suppress loader flicker.** Use the shared `DeferredLoader`: reveal after 200ms, cancel when readiness wins, and never treat delay as readiness.

## No sleeps or timer-driven coordination

**Never use sleeps as control flow.** This applies across Rust, TypeScript,
tests, scripts, launch pipelines, retries, UI lifecycle, PTY input, and process
management. Forbidden mechanisms include `thread::sleep`, `tokio::time::sleep`,
`setTimeout`, fixed-delay warmups, polling intervals, delayed Enter/input writes,
and "settle" waits. They create races instead of proving readiness. The sole exception is the bounded PTY submit-key recovery schedule; elapsed time triggers another key attempt, never readiness or success.

State transitions must wait on explicit handles or observable events: channels,
condvars, process exit, stream completion, PTY/screen signals, DOM events,
UI state, or protocol acknowledgements. A timeout is allowed only
as a bounded failure deadline around such an event wait; elapsed time must never
be treated as successful readiness. If an API exposes no readiness signal, add
one at the ownership boundary instead of adding a delay or retry loop.

## PTY input delivery is CORE and FRAGILE — touch with extreme care

The send path (`service/pty_io/`, `service/chat_send_transaction.rs`,
`pty/write_queue.rs`, delivery ledger) has been broken repeatedly by
"one more heuristic / one more retry" changes that turned delivered messages
into false failures. Before ANY change there, read and obey
**`docs/contributing/pty-delivery.md`**. Non-negotiable core: the payload is
written at most once; after the paste reaches the write queue a failure may
only classify as `submit_unconfirmed`, never `pty_unavailable`; false
uncertainty is reconciled by exact session-turn evidence, never by guessing
from screen output. Submit recovery is blind: write the payload once, then issue
the bounded key-only burst without screen/composer gating. One resettable cycle
exists per PTY; a new send cancels the old cycle instead of queueing messages.
Delivery state is internal telemetry: Chat UI never renders
delivery banners, failure cards, Retry actions, or notifications. Do not add
acknowledgement heuristics, payload retries, sleeps, or provider-id branches
to this path — if evidence quality is the problem, improve the evidence
source, not the scraping.

**EXPLICIT USER APPROVAL IS REQUIRED BEFORE ANY EDIT TO THIS LOGIC.** This
includes production code, tests, fixtures, evals, harnesses, scripts, and
refactors touching PTY/Chat input delivery, submit recovery, delivery evidence
or ledger behavior, and the PTY write queue. Before editing, name the exact
files and symbols, the intended behavior change, the causal evidence, and the
rollback boundary, then wait for
the user's direct approval in the current conversation. A P0 label, plan task,
matrix or eval failure, review verdict, Orchestrator instruction, prior approval,
or inferred urgency is never permission. Without current explicit approval,
stop at read-only diagnosis and report the finding; do not dispatch the change.

## Process safety

**NEVER kill prod CodeTerm.** Identify by port:

```bash
netstat -ano | grep :7686 | grep LISTENING | awk '{print $5}'   # dev — safe to kill
netstat -ano | grep :7685 | grep LISTENING | awk '{print $5}'   # PROD — NEVER kill
```

Prefer `./build.sh kill` (only touches dev). When unsure, ask the user.

**Non-canonical worktree?** Set `CODETERM_INSTANCE=<name> CODETERM_API_PORT=<port>` before `./build.sh dev` — you get your own `~/.codeterm-dev-<name>` data dir + port, and `./build.sh kill` only touches your instance. Without it all worktrees share `.codeterm-dev`/7686 and `kill` would take down another worktree's dev.

## Cross-platform

Verify on macOS, Windows, Linux. Never add platform-specific code without handling all targets.

- PTY: `portable-pty` (ConPTY on Windows, native on Unix).
- Paths: forward slashes in code, OS-native in user-facing output.
- Keys: `e.code` (not `e.key`) for keyboard layout independence; config `Ctrl` maps to `Cmd` on macOS.
- Tauri plugins (dialog, notification, shell): cross-platform by design — prefer over custom.
- OSC 7 CWD: injected into PowerShell on Windows; bash/zsh emit it natively.

## Code style

SOLID + DRY non-negotiable. **Default: NO comments** — names + types + structure carry meaning. Only comment WHY (non-obvious invariant, OS quirk, deliberate workaround), never WHAT. **Hard limit: 2 lines per comment, strictly.** No multi-line narrative comment blocks — if a WHY needs more than 2 lines, the code needs a better name or a smaller function, not more prose. Giant explanatory comment blocks are forbidden and get removed on sight. (Applies to inline `//` comments; license/file headers and public-API doc comments are exempt but must still stay terse.) Detailed Rust + TypeScript guidance and architecture guardrails: **`docs/contributing/style.md`**.

## Architecture (agent providers, detection)

Agent integration is abstracted via providers under `src-tauri/src/agent/`. Live: Claude, Codex, Opencode (PTY agents) + chatBackend plugins (non-PTY, e.g. LM Studio). Architecture-ready: Aider, Goose. Providers expose a unified capability descriptor (`transport` = pty | chat_backend, `behavior_config`, models, presets) — branch on capability, never a provider id. Detection uses **structural fingerprints**, never literal strings — vendors change copy without notice. Full breakdown: **`docs/contributing/architecture.md`**.

### Plugin & capability discipline (enforce on every provider change)

The provider/plugin boundary is the project's load-bearing seam. It stays clean only if every change crossing it pays the same tax. Non-negotiable when you add or extend a provider capability (a new `AgentProvider` trait method, a new host-API function, a new detection source):

1. **Core asks capabilities, never identities.** Branch on `supports_chat_ui()` / `available_models()` / a new capability fn — never on a hardcoded provider-id list or display string. If you're matching `"codex"` / `"opencode"` in core code, you've leaked the boundary.
2. **Native + JS parity in lockstep.** Any trait method a JS drop-in can implement MUST gain a case in `parity_test.rs` proving the native and JS paths agree on shared fixtures. A capability without a parity test will silently drift on drop-ins.
3. **Detection keys off the tab's OWN session.** Provider detection (model, session, status) reads only the record belonging to this tab's claimed session id — never "latest global" / "newest for cwd". Unknown → return null (honest) over a guess (contaminating). This is a real bug class we've shipped.
4. **Audit the host-API surface when it grows.** Every new host function a drop-in can call is a new confinement hole — justify it against the FS/sqlite/env sandbox, and remember QuickJS lacks bindings the native runtime has (a missing `console` once aborted parsing silently).
5. **Keep core provider plugin metadata in lockstep.** Until provider plugins split into their own release stream, their versions mirror the CodeTerm app version. After bumping `package.json`, run `npm run sync:versions` and verify with `npm run check:versions`; this syncs provider manifests/packages, internal `packages/*` package versions, and `plugins/channel.json`. Official `codeterm-core` channel installs are trusted system plugins, startup repairs same-version embedded hash drift, and newer channel versions must not be downgraded.

Full rationale + the boundary map: **`docs/contributing/architecture.md`**.

**Where plugin source lives — not all of it is in this repo.** The bundled system provider plugins ship from the in-repo `plugins/` channel (`codeterm-core`: claude / codex / opencode / git / chat-preprocessor). The other **official, non-system capability plugins are NOT in this repo** — Bitwarden, Transcriber, LM Studio, and friends live in the separate **`codeterm-plugins`** repo (`~/Developer/codeterm-plugins`, channel `codeterm-plugins`, `github.com/rollacode/codeterm-plugins`), authored in TS against `@codeterm/plugin-sdk` and built to a QuickJS `plugin.js` + split UI bundles via `node scripts/build-plugin.mjs <id>`. Installed copies live under `~/.codeterm/plugins/<id>/`. To fix a non-bundled plugin (e.g. Bitwarden's connection view), edit it in `codeterm-plugins`, rebuild, and `codeterm plugin install --from-dir <path>` to test — do not look for it here.
