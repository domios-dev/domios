# Agent spawn API
One-call agent creation, launch validation, placement, model routing, and response contracts.

### Agent Spawn (POST /api/agents/spawn)

Creates a new tab in the parent's workspace, assigns its role and launches the provider with an optional task. Each agent owns a tab; hierarchy is logical. Spawn never changes the active tab. Launch verdicts are bounded below.

**Request body:**
```json
{"agent":"opencode","title":"Reviewer","cwd":"C:/project","role":"Worker","parent_tab_id":"a3f1b2c7","task":"Review the changes","preset":"demo"}
```

The selected model's advertised reasoning levels constrain `reasoning_effort`; the provider's flat list applies when the model has none (`domios agent models <provider>` shows the sets). Provider listings may include `default_reasoning_effort` on the provider descriptor (fallback) and on each `available_models` entry (that model's live default). `domios agent models <provider>` marks the model-specific default beside its reasoning levels, falling back to the provider value only when the model has none.

`domios agent models <provider>` requests a catalogue refresh before every listing: providers that declare `liveDiscoveryRequired` re-probe and warn when the probe could not refresh, while any other catalogue gets the reader-gated re-probe (its TTL window, or a changed credential file, provider config, or provider binary). The authenticated `POST /api/agents/providers/refresh` endpoint accepts `{provider_id}` for the same explicit refresh; a failed probe keeps the last registered snapshot and reports `refreshed: false` with a `reason`. The CLI warning quotes that reason; with `--json`, stdout stays the model array and stderr carries `{"warning":"live_model_discovery_not_refreshed","provider","reason"}`.

Fields are optional; `agent` defaults to the configured provider unless a unique model selects another. `cwd` must be absolute and exist on the receiving host or spawn refuses before tab creation; the CLI resolves relative `--cwd` locally. Titles: one word, at most 64 characters. `description`: one line, at most 200 characters. Both refuse control characters. Workers default to full machine access for either execution intent. Optional `sandbox: "read-only"|"workspace-write"` explicitly requests provider confinement for this launch; unsupported mappings are refused. When the caller (`X-CodeTerm-Tab-Id`, `spawned_by_tab_id`, `creator_tab_id` or `parent_tab_id`) has a recorded sandbox, or `agent.sandbox_ceiling` is set, a `sandbox` above that ceiling, or none, is refused with `403 sandbox_ceiling`; under a workspace-write caller the `cwd` must lie inside its writable roots. Other agents follow the global `agent.full_access` choice and refuse an unset choice before tab creation. Saved sandbox policies remain immutable. Without full access, a model the provider declares without an unattended permission mode receives launch-scoped grants for the role's Domios commands, and an Orchestrator or Planner on such a model is rejected before tab creation with an error naming the model (`team pair` checks both members first). `audience` controls user notifications only. With an authoritative model catalogue, an unknown `model` is rejected before tab creation (`domios agent models <provider>` refreshes and lists valid ids); free-form providers validate against a published live model list and pass ids through only when no live list exists. An id advertised by several providers requires an explicit provider, and provider aliases are never passed across providers. Reasoning effort is capability-validated before launch, and a level the provider lists without a launch flag for it is refused; response provenance separates host-owned `planned` plan-task intent from client `requested`, provider `resolved`, and exact-session `actual`; ordinary spawn payloads cannot set `planned`. `task` goes through the provider's declared launch delivery; `agent_name` maps to the provider's named-agent launch option when supported. The CLI flag `domios agent spawn --non-user-facing` sends `audience=automation`. A `Worker` with `execution_intent: "read_only"` needs no task binding: it owns and transitions no task, and `authorized_gates` is its whole command scope, rendered into its brief. For a plain Worker, `execution_intent: "mutating"` without `plan_task`/`task_id` is refused; Worker kinds may do assigned mutating work without a task, and `authorized_gates` is rejected alongside `plan_task` (a task-bound Worker declares gates on `plan.task.dispatch`, where they are enforced). Task-bound mutating spawns require `cwd` to be a branched worktree lane owned by this task; missing checkouts, canonical and foreign lanes refuse before tab creation. Use `domios plan task dispatch` to provision it. Worker `role_profile` adds a leaf kind prompt (such as `qa` or `release_manager`) to the Worker base; managing kinds are refused. `domios plan task dispatch` sets it from the task's `executor_role` when that role names a builtin leaf.

`audience` is `user` (default) or `automation`; an automation or hidden tab's prompts and exits never notify the user and are reported to its parent or report target instead (`domios docs NOTIFICATIONS`). `description` is validated like a tab description, and `reasoning_effort` is never silently downgraded. Routing is **by capability, not identity**: an `agent` matching a `chatBackend` shell id opens an agent shell (`system_prompt`/`preset`/`model` and watcher `mode`/`engine` reach its `openSession` ctx); otherwise the PTY agent path, which refuses the chatBackend-only fields (`system_prompt`, `charter`, `tick_interval_secs`, `nudge_cooldown_secs`, `max_actions_per_tick`; `preset` is accepted only through a declared model-provider configuration capability) and names them, just as a chatBackend shell refuses PTY launch `args`. `role` accepts `Orchestrator`, `Manager`, `Worker`, plus `Planner`/`Watcher` sugar that maps to `Manager` with `role_profile`. A `Planner` spawn requires `plan_id` and resolves an omitted parent as the role endpoint does. Watcher spawns require a watcher-capable `chatBackend` shell and `charter`; policy fields are clamped by the host. An unknown id errors with the available agent **and** shell ids. `report_to` sets where the worker's `agent report` lands (Tab id or `main`/`general`). `origin_peer` is **never client-supplied**: the mesh relay stamps it from the authenticated sender so a mesh-spawned worker reports back (*Remote mesh workers*). `team_id` + `creator_tab_id` (`domios agent spawn --team`) attach a ROLELESS agent to an existing Team: `creator_tab_id` must belong to `team_id`, and the pair is rejected with `role` or `plan_task`. Membership is checked before tab creation, so a refusal leaves nothing behind. Socket `team.adopt_agent` applies the same check to an already-running tab; see API-TRANSPORT. A **roled** Team member (including a replacement Orchestrator) uses `POST /api/teams/{team_id}/members` / socket `team.add_member` (API-TEAMS).

Task-bound canonical mutating placement uses parent-authorized `plan task dispatch --execution-intent mutating --canonical-writer`, which reserves one exclusive task attempt before creating the Worker. Direct `agent spawn --plan-task` cannot reserve that attempt and remains refused for task-bound canonical mutation. Task-less Worker kinds with Plan context retain parent-directed placement behavior and do not reserve task attempts or participate in canonical writer occupancy, so the parent coordinates those canonical writes. Local dispatch may pass `--kind qa` or `--kind release_manager` to select the built-in prompt profile without changing the saved `executor_role`; the kind grants no placement or publication authority.

An unknown id on an authoritative catalogue or a published free-form live list is refused before spawn or task dispatch creates a tab. REST spawn returns HTTP 422 with `error.code` set to `invalid_model`, including `provider`, `requested_model`, `valid_model_ids`, and `refresh_command`. A bare id owned by multiple providers returns `ambiguous_model` with `ambiguous_providers`; choose the provider explicitly. Neither refusal has a transient retry hint. CLI `--json` preserves these fields under the error envelope's `data` for spawn, dispatch, and team pair.

**Response** (after the launch verdict, bounded at 20 s):
```json
{"tab_id": "a3f1b2c7", "pty_id": "c9d0e1f2", "agent": "claude", "title": "Worker-1", "role": "Worker", "launch_state": "ready"}
```

`launch_state` is `ready` once the agent is ready, or `starting` with a `warning` when it waits on an owner prompt, holds a provisional boot stage, or is still launching at the bound; `starting` never claims readiness. A provider that exits before readiness fails the spawn: REST answers 500 with `error.code` `launch_failed`, socket `agent.spawn` returns the same fields as error `data`, and the CLI exits non-zero. Both carry `tab_id`, `reason`, `output_tail` (the provider's last printed lines), and `retry_hint`; the failed Tab stays in `spawn_failed` for inspection. `plan task dispatch` reports the same failure, output tail included, through its startup-failed event.
