What the button does
A fourth action kind. The existing three cannot carry an answer anywhere.
1
The agent asks, writing the body through its pad
codeterm notify send "Delete the stale win32 baselines?" \
  --level action-needed \
  --from-pad ask.md \
  --answer "Delete them" --answer "Keep, mark unproven"
The body is only ever a pad path. An inline body is refused, so a shell never mangles a question before the user reads it.
2
The card records who asked, before you answer The asking tab is captured at send time, not resolved at click time. A tab that dies between the ask and the tap leaves the card answerable-but-undeliverable, and it says so instead of failing silently.
3
You tap. The label is delivered to that tab as a routed message
-=-codeterm:answer notification=n_4f2a-=-Delete them
It arrives on the same routed-message path a tab reply already uses, so the agent needs no new reading mechanism — only a marker it already knows how to recognise.
4
The card becomes a record of what you chose One answer per notification. A second tap does nothing — the buttons are replaced by the answer, so the panel stays an honest log of decisions rather than a set of live controls.
The existing action kinds are invoke, url and dismiss. None routes anything back to a tab, which is why an answer needs its own kind rather than an invoke carrying a tab id in its arguments — that would let any notification call any command.
