What this costs to compute, and where it should live

Measured, not estimated

A full extraction for this plan, tokens.py, read 14 session files, 63.0 MB, 15,919 lines, and took 0.4 s wall time on this machine with the files warm in the cache, 1.6 s cold, including the plan store read and the event list. Reading only the last 64 KB of each file, which is what an incremental pass does, took 0.025 s for 0.9 MB.

Scaled to a day rather than a plan: this machine touched 74 Claude logs (142 MB) and 50 Codex rollouts (166 MB) today, so a whole-day full pass is about 8 s at the cold rate, and an incremental pass stays under a second. Everything on disk is 1,299 Claude logs (1.2 GB) and 2,638 Codex rollouts (39 GB); a full rescan of history is not something to do on open, and never needs doing, because the figures are additive and a cursor per file makes every later read incremental.

Verdict: cheap enough to run on open for one plan, cheap enough to run continuously behind cursors, and a schedule buys nothing. The board is arithmetic over fields; there is no model call anywhere in it.

The ledger that already exists

The KPI ledger in src-tauri/src/agent/kpi_ledger.rs is a SQLite table kpi_events with plan_id, task_id, tab_id, role, provider, model, timestamp, kind, bytes, three token columns input, uncached_input, output, and a dedup_key. Its kpi_usage_cursors table keeps a forward-only read offset per session file. kpi/usage/records.rs parses the two record shapes tokens.py parses: Claude's message.usage with cache read and cache creation, and Codex's payload.info.last_token_usage with cached input. kpi/recorder.rs ingests from the cursor and writes one batch per file. It is off on this machine: kpi.enabled is false and no kpi_ledger.db exists.
