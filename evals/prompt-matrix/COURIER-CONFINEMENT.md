# Courier fixture confinement proposal — pending owner/Orchestrator disposition

This is a source proposal for the existing Courier task `task_2exdlb`, not approval to edit the daemon, re-open accepted work, opt into updates or execute an installer. Probe owns only the harness. `prepare` still writes `allow_provider_updates_in_non_prod=false`; CoordinatorScenario never changes it.

## Observed source boundary

`provider_update.rs::install` calls `provider_update/command.rs::run_update_command(update.command)`. `update_argv` resolves the provider capability's first token with `js_runtime::probe_bin`. `src-tauri/crates/codeterm-plugin/src/js_runtime/bin_resolve.rs` searches PATH, persisted Windows machine/user PATH and rescue directories. A fixture PATH does not exclude global executables. The daemon updater inherits the daemon environment, not a prompt tab's npm registry override. The old provider-only failure override is removed.

Pinned Codex 0.159.3 [CLI source](https://raw.githubusercontent.com/openai/codex/rust-v0.159.3/codex-rs/cli/src/main.rs) calls its real update action. The [action source](https://raw.githubusercontent.com/openai/codex/rust-v0.159.3/codex-rs/tui/src/update_action.rs) chooses npm/bun/pnpm/vp/brew or standalone installation. The npm action is `npm install -g @openai/codex`, with a mutable default target. Standalone invokes the external shell/PowerShell installer. npm prefix alone confines neither native resolver choice nor standalone destination. The [install context](https://raw.githubusercontent.com/openai/codex/rust-v0.159.3/codex-rs/install-context/src/lib.rs) also interprets managed-package environment flags. The fixture native launcher reproduces the pinned npm wrapper's own flags and package-root metadata; those flags are not confinement evidence.

`run_update_command` waits 300 seconds, terminates its process tree, and reports stopped when the parent completed or subsequently exited. `process.rs::ProcessTree` uses a Unix group or Windows job, but the returned fact is not a complete descendant-empty receipt. `Dev`'s case deadline is 180 seconds. Runner failure must cancel the admitted updater and independently observe the entire tree stopped; raising the case cap does not resolve that gap. Storage is already under isolated daemon HOME, `.codeterm/provider-update-state.json`; no storage edit is currently justified.

## Smallest proposed owner boundary

| Boundary | Required bounded behavior | Independent receipt |
|---|---|---|
| `provider_update.rs::install` | Accept a reviewed fixture scope only for the explicitly named nonprod instance, while retaining default disabled configuration and existing admission semantics | Scope id, provider, exact target and actual capability command captured before spawn; no owner paths |
| `command.rs::update_argv/run_update_command` | Resolve the updater to an absolute, byte-verified fixture executable; refuse implicit PATH/rescue resolution for that scope | Actual argv, executable SHA256 and selected native/package tree, not an intended path |
| Same command boundary | Supply only fixture-owned HOME/config/cache/temp, reviewed real npm executable and native destination prefix; refuse standalone/brew/unknown installation methods in this fixture until their destinations can be proved | Real child environment names/owned paths, npm install argv and all write destinations; no credential values |
| Same command boundary | Bind capability target to reviewed 0.160.0 before admission and the real package installation; refuse mutable target drift | Actual installer package/version and byte/tree receipt; registry metadata alone is insufficient |
| Same command boundary | Inject deterministic failure only into the actual daemon updater's owned registry/command environment, using a nonce-bound local failing registry and a real npm child exit | Real updater child identity, real registry request, nonzero exit and captured error; never a stub success/failure result |
| `command.rs` / `process.rs::ProcessTree` | Give the fixture command a bounded deadline within the existing cell budget and an explicit cancellation/completion handle; retain real tree ownership and observe all descendants stopped before cleanup | Parent exit plus independently complete group/job termination and stream closure; parent exit alone is insufficient |

A fixture wrapper may record the verified actual argv/environment path names and exec the real native updater. It may not replace it with a scripted status, write coordinator state/journal, simulate restarts or manufacture recipient receipts. An npm wrapper that pins the actual real installation needs explicit review of both its argv transformation and real native destination layout; it is not implicitly approved here. No CLI/config command enabling this proposed fixture scope exists or is invented in GATES.md.

Rollback boundary, if approved: the bounded nonprod fixture command scope and its explicit receipts only; default-disabled admission, production capability handling and existing product policy remain unchanged. Resolver changes outside that scope are not requested. The owner/Orchestrator must decide whether this is needed and assign any actual daemon repair through Courier. Probe will then bind the reviewed producer receipts, not implement that repair.

## Other blockers stay separate

The Codex [startup update source](https://raw.githubusercontent.com/openai/codex/rust-v0.159.3/codex-rs/tui/src/updates.rs) returns no popup version when `check_for_update_on_startup=false`. CodeTerm's `plugins/provider-codex/src/plugin.ts` sets that value in fresh and resumed launches. `codex update` is an installer entrypoint, not the TUI Skip picker. Neither an older package nor seeding version.json supplies an authentic prompt while that gate is false. No production flag is removed and no fake prompt is used; supported authentic trigger proof is still missing.

Auditor's exact action-envelope join and the retained paired-observation criteria remain pending. Current safe-choice journal rows are pre-input authorization, not provider-side occurrence receipts. A failure needs an explicit completed observation barrier for zero restarts, without new disconnected observer work. Public own-tab chat provides optional `toolCallSourceId`, `toolPairing`, `toolExitCode`, `toolInput` (raw input), `toolArgs` (display detail), `toolId`, `toolResult`; missing or unavailable pairing stays unavailable. Current Codex plugin source does not establish all those exact pairing fields. The harness must not infer them from row position or output text. Fixture-owned authentication readiness, owner oracle/admission/PTY decisions, Cursor unsupported update and final-head Windows evidence remain separate requirements.


The current fixture scope pins the older executable immutably. It must not be promoted to the separately preassembled target just because a restart is claimed. After a confined real install, a follow-up source binding must select the actual installed destination and verify its target bytes/tree/version before permitting resumed launches. Unscoped daemon executable probes also refuse through the strict provider launcher; any required bootstrap probe must gain a separately bounded, fixture-native binding, not an owner-binary fallback. These are source integration gaps, not reasons to launch early.
